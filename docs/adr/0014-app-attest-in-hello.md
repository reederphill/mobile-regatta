# App Attest rides in Hello, and the counter stops replays

Every service connection proves it comes from the genuine Regatta app on a real Apple device with App Attest. The proof is in `Hello`, before the session call. A connection without a good proof can't queue, chat or race. Built in [#158](https://github.com/reederphill/mobile-regatta/issues/158), for #26's "Genuine client" line.

## The decisions

- **The proof is in `Hello` (schema 1 of `Hello.attestation`).** A new key sends its attestation; every later connection sends an assertion. Both sign `SHA256(clientData)`, where clientData is `purpose | 16-byte nonce | SHA256(the session call's WirePlayer)`. No extra round trip, and no change to the 10 s sign-in deadline. `HelloAck` says what the proof came to: not checked, verified, bypassed, key unknown, or failed.
- **The counter is the replay defence.** Each assertion's counter must be above the stored one. The key store's `UPDATE … WHERE counter < $new` makes that an atomic compare-and-set: of 8 concurrent advances to the same counter, exactly one wins. The nonce makes every clientData unique. There is no check of the client's clock. A pre-computed assertion is only as good as a relay through a genuine device, which a server challenge wouldn't stop either. An attestation is a key's first use, once: registration is insert-only and atomic (`INSERT … ON CONFLICT DO NOTHING RETURNING`), true only for the call that stored the key, and it is the only check. A second attestation of a registered key, under its public key or another, is refused as a replay, and of two copies of one attestation checked at once exactly one is verified. An assertion's stored key must also be of an environment the server still accepts.
- **The chain is verified at the server's `now()`, last.** The credential certificate is short-lived, so an old attestation can't be replayed past its validity. `x5c` is exactly two certificates, the credential certificate and its intermediate, as App Attest sends it; any other count is refused as malformed before a certificate is parsed, and only `x5c[1]` is handed to the chain search as an intermediate. A pre-sign-in `Hello` is anyone's to send: layered same-subject intermediates made the search try m^k paths (129 s of CPU for one 14.5 KB `Hello`, PR #589's review). The nonce, key id, RP ID, counter, AAGUID and credential id are compared first, so the signatures are checked only for an attestation that could be good. The whole check has a deadline (`checkDeadline`, 5 s, as the gate's store reads have): past it the connection is unattested.
- **The restriction flags ride in the asserted request.** The binding is the hash of the `WirePlayer` the session call then sends, so the underage, communication and multiplayer flags are what the device signed. A session call naming any other player (other flags, another alias) makes the connection unattested for good, and ends what it held: her place in the queue and her lobby feeds. The flags are Apple's word only on an attested connection, and only an attested connection reaches the queue, the lobby and races.
- **An unattested connection is closed to the queue, the lobby and races, and nothing else.** The queue answers `attestationFailed` ("Can't race online right now"). The lobby shows as restricted, `communicationRestricted`: its flags can't be trusted, and chat safety rests on them (owner, O1). A race-session call answers as having no race and leaves the connection open, so the client doesn't reconnect in a loop. The profile, the terms and Delete my online data work. Practice is never touched.
- **A failure is that connection's only.** Nothing writes `players.attestation_failed`: it stays a stored lever for a person's decision, because #26 says penalties are never automatic. Each failure logs one stderr line with its reason and never the key id, at most one a reason a minute (with a count of those held back), so a flood of bad `Hello`s isn't a flood of lines.
- **Race connections carry no proof (our reading of #26's "each online connection").** A `/race` connection's credential is its race token. Outside dev (`SeatAuthPolicy.raceToken`) only the queue mints one, and the queue serves only an attested, signed-in service connection; anything but a `JoinRace` with a valid token is refused. Asserting on `/race` too would need an async proof inside the race join and the polled rejoin, and it would double the counter races.
- **Apple unavailable: fail closed, retry quietly.** The server needs no Apple service at run time: the receipt is stored, not checked against Apple's fraud metric. On the client only `attestKey` talks to Apple. When it fails `serverUnavailable`, the key is kept, `Hello` says `unavailable` and the connection opens unattested. The attester tries `attestKey` again on every later connection, and a queue refused for attestation while Apple was unavailable reconnects once after 5 minutes, in the foreground. There is no grace period: #26 says a failed attestation can't queue. An outage doesn't touch a device that has already attested, because assertions never need Apple.
- **Devices that can't attest can't race online.** On the simulator `isSupported` is false and `Hello` says `unsupported`, which only the dev bypass lets through. Outside the simulator (perhaps the iPad build on an Apple-silicon Mac) the player gets "Can't race online right now", and #55 turns off "available on Mac" (owner, O2).
- **`attestKey` is one-shot.** The attestation object stays in memory only, never on disk. If the server doesn't acknowledge it in the session, or refuses it, the client makes a new key (a record left unattested by an earlier launch is replaced, never attested again), and so does any `attestKey` failure but `serverUnavailable`; `keyUnknown` (the server lost the key) does the same. A failed assertion is retried once at once with a fresh one: the service connection and a reconnect can overtake each other's counters.
- **The bypass is dev-only.** `APP_ATTEST_BYPASS` is on by default in dev so the load client, the contract runner, e2e and the simulator work. It accepts no proof or `unsupported` as bypassed, but a real proof is still verified, so a dev build on a device exercises the real path. Outside dev any value but `off` (or unset) refuses to start. The setting itself defaults off, and only `ServerConfig.load` in dev (and `ServerConfig.dev()`) turns it on; `ServiceEndpoint` has no default attestation, and `ServiceEndpoint.make` and `RegattaHTTPServer.start` refuse a bypass outside dev, or production taking any keys but production's, from a hand-built config or a handed-in endpoint alike.
- **Environments follow the entitlement.** The AAGUID is `appattestdevelop` or `appattest` and seven zero bytes, as the app's `com.apple.developer.devicecheck.appattest-environment` entitlement (`APP_ATTEST_ENVIRONMENT`) sets it. Production accepts `appattest` only; staging and dev accept both by default: Debug builds on registered devices attest as development, and TestFlight builds as production.
- **Staging and production can start.** `ENV=staging|production` exist now, with `REGATTA_DATABASE_URL` required: keys in memory would be forgotten at a restart. Any other `ENV` value still refuses to start.
- **Apple's root is embedded.** `AppleAppAttestRoot.pem` is Apple's App Attestation Root CA, downloaded with curl from <https://www.apple.com/certificateauthority/> (`Apple_App_Attestation_Root_CA.pem`, 2026-10-22), valid to 2045-03-15. The SHA-256 of its DER is `1cb9823ba28ba6ad2d33a006941de2ae4f513ef1d4e831b9f7e0fa7b6242c932`, and `AppleRootTests` pins it. Tests inject their own root.
- **Our own CBOR decoder.** Following ADRs 0006 and 0009's dependency stance: about 150 lines, five major types (unsigned, byte string, text string, array, map), lengths in the 1-, 2- and 4-byte forms. It refuses indefinite lengths, tags, floats, negative integers, duplicate map keys, more than 64 items in an array or map and nesting deeper than 4. It never traps, and never reserves past its input; it's fuzzed over 10,000 inputs.
- **Hard refusals.** The key id must equal SHA256 of the credential certificate's public key (uncompressed, 65 bytes), and the authenticator data's credential id must equal the key id. Neither is ever a warning.
- **The key id is kept in the Keychain, this device only, from the first unlock** (`kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`): a connection made from a background launch while the device is locked still finds it. The attester reads it on first use, not when it is made.
- **Keys have no player link.** A key is the install's, not the player's (`app_attest_keys`, migration 0018), so Delete my online data (#160) has nothing to erase there. The retention job purges keys unused for 730 days, the inactivity horizon.

## Verified against a real device

A public real-device vector, `ios-14.4.yaml` from [veehaitch/devicecheck-appattest](https://github.com/veehaitch/devicecheck-appattest) (Apache-2.0; the licence is in `Packages/RegattaServer/Tests/Fixtures/real/LICENSE`), is converted to `Fixtures/real/app-attest-public.json`. `RealAppAttestTests` verifies it on every run, at its own timestamp, against the embedded root, with its own team and bundle id. Its attestation and its assertion (counter 1) both verify. That confirms the nonce extension's shape (`SEQUENCE { [1] EXPLICIT OCTET STRING }`) and the signature convention: ECDSA-SHA256 over the nonce, so the nonce is hashed again. It also showed that App Attest sets the attested-credential flag in an assertion's authenticator data too, so the parser reads an attestation's or an assertion's by the caller, never by the flags. The vector's Hello fits the 16 KiB pre-sign-in frame. #175's own capture (`-captureAppAttestFixture`, `Fixtures/real/app-attest.json`) runs too, when it's there.

## Considered and rejected

- **A server challenge in `HelloAck`, with the assertion in the session and race calls.** It follows Apple's "server challenge" guidance more literally and stops pre-computed assertions. But the proof leaves `Hello`, every session and race call changes, and a relay through a genuine device defeats it as well.
- **An assertion on `/race` too.** It would need an async proof before the race join and inside the polled rejoin, and it would double the counter races. The queue-minted, seat-bound, 600 s race token carries the attested connection's word instead.
- **A CBOR package.** It's a dependency for five major types.
- **Apple's root as an environment variable**, like `REGATTA_APPLE_ROOT_PEM`. The root is public and valid to 2045: a constant with a pinned fingerprint can't be misconfigured.
- **Writing `attestation_failed` on a cryptographic failure under a known key.** That would be an automatic penalty, and #26 says a person reviews every one.
- **A grace period when Apple is down.** It would let an unverified client race.
- **Apple's sample in the "Attestation Object Validation Guide" as the real vector.** A forum report (FB24281098) says its values are inconsistent.

## Consequences

- Until #49 sets up the App ID and #175 captures a device's attestation, only the public vector proves the format against real bytes. #175 must run before the first non-dev deploy (#167), as it must for Game Center (ADR 0010).
- The App ID is `REGATTA_TEAM_ID.REGATTA_BUNDLE_ID`, README's values until #49 confirms them. A wrong team id refuses every attestation (`wrongAppID`).
- A connection whose proof fails sees the lobby as restricted even if the player isn't: the cost of not trusting its flags.
- The fraud-metric receipt is stored and never read. Checking it with Apple would be a runtime dependency; it's left for when abuse shows up.
